Experiment log

Project aim: predict how a piano performance's dynamics (loudness) and tempo (speed) change over time, using only the audio. The MIDI file recorded with each performance is used only to create the "correct answers" for training. The model never sees the MIDI when it makes a prediction.

Data: 10 performances from the MAESTRO v3.0.0 dataset (audio WAV + matching MIDI), kept in test_data/. This is a small test subset for checking the pipeline, not the full dataset.

EXP-01: Data check: are the audio and MIDI usable? (notebook 03_test_exp, 8–9 Oct 2026)

ItemDetails
QuestionDo the WAV and MIDI files line up, and which MIDI information can be used as training targets?
What I didPaired each WAV with its MIDI file (10 pairs found). Loaded the first pair, plotted the mel-spectrogram and the MIDI note velocities, and read the MIDI tempo markers. Then compared audio loudness (RMS in dB, one value per second) with the mean MIDI velocity in the same second.
Results • Audio: 44,100 Hz, 2 channels (stereo), 434.9 s long.
• MIDI: 5,126 notes. Velocity min / mean / max = 3 / 68.7 / 123 (scale 0–127).
• Tempo markers: only one value, 120 BPM, for the whole piece.
• Loudness vs velocity correlation: r = 0.73.
What it means • r = 0.73 is a strong positive correlation: when the MIDI says notes are played harder, the audio really is louder. So the files are aligned in time, and MIDI velocity is a good target for dynamics.
• 120 BPM is the default value MIDI software writes when it doesn't know the tempo, so it is a placeholder, not the performer's real tempo. The tempo target has to be calculated from the note timings instead.
LimitationsThe alignment check used only one file. The audio is stereo at 44.1 kHz, which led to the preprocessing tests in EXP-02.
Outputsresults/plots/01_mel_spectrogram.png, results/plots/01_audio_vs_velocity.png

EXP-02: Preprocessing comparison (notebook 04_preprocessing, 12 Oct 2026)

ItemDetails
QuestionWhich audio preprocessing settings keep the information needed to predict dynamics and tempo, while keeping training cheap?
What I didTested 7 settings (sample rate, mono/stereo, loudness normalisation, segment length, number of mel bands, hop length, dB reference) on the 10 pairs, using the first 2 minutes of each file. Details and numbers are in the Preprocessing comparison tab.
Main resultThe most important finding: any normalisation per segment (per clip) destroys the loudness information. The correlation with velocity drops from 0.72 to 0.06 or 0.00. In the same way, a dB scale referenced to each clip's own maximum lowers the correlation (0.60 vs 0.77 with a fixed reference).
OutcomeFinal pipeline: 22,050 Hz, mono, no amplitude normalisation, 5 s segments, 128 mel bands, hop 512, dB with fixed ref = 1.0, then standardise using training-set statistics only. See the Decision log tab.
Outputsresults/preprocessing_results.csv, results/plots/02_n_mels.png

EXP-03: First model comparison: CNN vs CRNN vs CNN + Transformer (notebook 05_models, 12 Oct 2026)

ItemDetails
QuestionWhich model type predicts dynamics and tempo best from mel-spectrograms? Do any of them do better than just guessing the average?
Data10 pieces, first 180 s of each, cut into 5 s segments, giving 325 segments. Each segment is a mel-spectrogram of 128 mel bands × 215 time frames.
Split by piece (a piece is only ever in one set): 6 pieces for training (197 segments), 2 for validation (56 segments), 2 for testing (72 segments).
Targets (what the model predicts, for every frame) • Dynamics: average velocity of the notes sounding at that moment, divided by 127 (so 0–1).
• Tempo: how many notes start in a 3 s window around that moment, compared with the piece's usual rate, on a log2 scale. 0 = normal speed, +1 = twice as busy, −1 = half as busy (clipped to ±1). Chords count as one onset.
ModelsAll three share the same CNN front end (3 convolution blocks), which turns each spectrogram frame into a feature vector.
• CNN only: predicts each frame on its own (188k parameters).
• CRNN: adds a bidirectional GRU, so each frame can use context from before and after it (262k parameters).
• CNN + Transformer: adds 2 self-attention layers instead of the GRU (480k parameters).
• Baseline: always predicts the training-set average. Any useful model must beat this.
Training setup8 epochs, Adam optimiser (learning rate 0.001), batch size 16, mean squared error loss, seed 42, CPU. After each epoch the model was checked on the validation set, and the epoch with the lowest validation loss was kept for testing.

Test results (lower is better for every error column, best value in each column in bold):

ItemDetails
How to read the metrics • MAE (mean absolute error) = the average size of the error. RMSE is similar but punishes big mistakes more.
• Dynamics errors are in MIDI velocity units (0–127). A dynamics MAE of 22.4 means the predicted loudness is off by about 22 velocity steps on average.
• Tempo errors are in log2 units. A tempo MAE of 0.35 means the predicted speed is off by a factor of about 20.35 ≈ 1.27, i.e. roughly 27% too fast or too slow on average.
What it means 1. All three models learn something real. They all beat the baseline on both targets. Dynamics error fell from 27.2 to 22.4 (about 18% better), and tempo error fell from 0.54 to 0.35 (about 36% better, CRNN).
2. Tempo: CRNN is best. This makes sense, because tempo depends on how notes are spaced over time, and the GRU can look at neighbouring frames.
3. Dynamics: no clear winner. The three models are within 1.5 velocity steps of each other. With only 2 test pieces and one training run (one seed), a difference this small could just be chance.
4. The bigger model is not better yet. The Transformer has nearly 2.5× the parameters of the CNN but is not better overall, and its validation loss jumped around (0.17 → 0.24 → 0.17 between epochs 5 and 7). That is typical of a large model trained on very little data.
5. Signs of overfitting: training loss kept falling (CRNN: 0.196 → 0.069) while validation loss stopped improving at about 0.13–0.16, so the models start memorising the 6 training pieces.
Limitations • Very small dataset: 10 pieces, only 2 in the test set.
• One run per model (seed 42). The results need repeating with several seeds to know whether the differences are real.
• Only 8 epochs. The training may not have finished.
• The tempo target is note-onset density (how busy the music is), not true beats per minute.
• Frames where no note is sounding get a dynamics target of 0 (silence), which may inflate the dynamics error.
• Only the first 180 s of each piece was used.
Next stepsTrain on more of MAESTRO; repeat with 3–5 seeds and report mean ± spread; train longer with early stopping; look at how silent frames are handled in the dynamics target; plot predicted vs true curves for a test piece.

Preprocessing comparison

All tests use the 10 WAV + MIDI pairs, first 2 minutes of each file (notebook 04_preprocessing, 12 Oct 2026). Where a test uses a correlation (r), it measures how closely audio loudness follows the MIDI velocity: 1 = perfectly, 0 = not at all. Higher is better, because the model has to read loudness from the audio to predict dynamics.

Notes for discussion: (1) In P3, per-file peak normalisation scored slightly higher than none (0.75 vs 0.72). The difference is small, and "none" was kept because it is simpler and the training-set standardisation in P7 already handles the overall scale. It would be fair to test per-file normalisation in a model later. (2) P5 and P6 were decided by inspection and reasoning, not by training models with each option.
